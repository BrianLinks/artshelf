## The decision that matters: public MIT, or private and proprietary?

MIT lets **anyone** use, copy, change and sell the code, including to train AI models, without asking you or paying you.
That is the right choice for a portfolio piece you want others to reuse. It works against your plan to sell licences, because
a buyer can already do what the licence would grant them.

| Goal | What to do |
|---|---|
| Show the project and let people reuse it | Keep the repository public under MIT (what is set up now) |
| Earn money from licences to AI labs | Keep the repository **private** (or remove public access), and give buyers rights through the sale itself; consider a proprietary license in place of MIT |
| Both | Publish a small public demo or the documentation, and keep the full source private |

Changing later is possible, but anything already copied under MIT stays MIT for the people who copied it. If selling is the
goal, decide before the repository is widely visible.

To switch to proprietary: replace `LICENSE` with the text in `LICENSE-PROPRIETARY.template.txt`, change `"license"` in
`package.json` to `"UNLICENSED"`, and update the README license line. Have a lawyer review the template first.

## Before you sign any licence (checklist)

1. **You own what you are licensing.** Nothing written for an employer, school or client; nothing copied from other projects without permission.
2. **AI assistance.** Read the buyer's terms about AI-assisted code. Rights in machine-generated work differ by country, so state the assistance honestly (it is disclosed in `NOTICE.md`) and ask a lawyer how it affects what you can promise. Do not claim sole authorship of every line.
3. **No secrets or personal data in the repository or its history.** Run the checks below.
4. **Third-party material.** Licenses of dependencies are compatible with what you are doing (command below).
5. **Keep the history.** Real, small commits are part of what is valued. Do not squash or rewrite them.
6. **The README matches the code.** Commands in it work from a clean clone.

## Commands (PowerShell, in the project folder)

Check that you are in the right repo first:

```powershell
git rev-parse --show-toplevel
```

Look for committed secrets or environment files:

```powershell
git ls-files | Select-String -Pattern "(^|/)\.env$|\.db$|\.pem$|\.key$"
git grep -nEi "api[_-]?key|secret|password|token" -- . ":!package-lock.json" ":!docs" ":!*.test.ts" ":!web/src/pages" ":!src/seed"
```

The first command should print nothing. The second will show some harmless matches (field names such as `password`); read each one and make sure none is a real credential. Search the history too:

```powershell
git log --all --oneline -S"BEGIN PRIVATE KEY"
```

Produce a list of dependency licenses:

```powershell
npx license-checker --production --summary
```

Anything marked GPL or AGPL needs a closer look before you license the code to others.
